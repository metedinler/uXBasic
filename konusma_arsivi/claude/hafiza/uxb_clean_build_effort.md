**MILESTONE (2026-09-07): first clean from-scratch build succeeded** (`compiler/scripts/build_uxb_main_64.ps1 -Force`, exit 0, `bin/uxb.exe` rebuilt). Root-caused and fixed roughly 20 distinct pre-existing bugs to get there, all unrelated to the DIM/BYREF feature work itself except where noted. Categories found (useful as a checklist if this ever regresses again):
- **Cross-file/cross-bundle ordering** (a function used before its defining file is included): `MIRFindClassDeclNode`, `SemClassMethodHasFlag` (same-file, used-before-defined), `MIRLowerMemoryOperandPatch4`, `UXBSurfaceLayerStatus`, `UXBWatDefaultMemory`, `UXBRuntimeBrowserDispatch` (also needed real content, not a stub — see below), `MIRX64EmitMethodCallSynthetic`/`MIRX64FindUserFunctionIndex`. Fixed via `Declare Function` forward-declarations (this codebase's established idiom) or by moving/removing a too-early `#include`.
- **The same file included via two different relative-path spellings** (FreeBASIC's `#include once` here dedupes by the literal path string, not the resolved file) causing "Duplicated definition": `array_memory_ref.fbs`, `parser.fbs` (pulled from `codegen/x64/*.fbs` via `../../parser/parser.fbs` vs the frontend bundle's `../parser/parser.fbs`), `mir_x64_codegen.fbs`. Fixed by removing the redundant later include, keeping only the earliest one.
- **FreeBASIC reserved-word collisions**: a parameter literally named `pos` and a local array literally named `chain` silently collided with FreeBASIC's own built-in `POS`/`CHAIN` keywords, producing confusing "Duplicated definition"/"Type mismatch" errors that look identical to the include-order bugs above but have nothing to do with includes. Fixed by renaming (`pos`→`posIdx`, `chain`→`ctorChain`). **Worth remembering as a distinct diagnostic category** if a "duplicated definition" error ever resists an include-order fix.
- **Two independent, genuine copy-paste bugs**: a `Case "PEEKS"` branch in two unrelated keyword-classification tables (`uxb_surface_registry.fbs`) and one MIR evaluator (`mir_evaluator_tail_controlflow.fbs`) had been overwritten with an unrelated `UXBSurfaceLayerStatus(surfaceText, layerText)` call (referencing undeclared variables) instead of the correct value matching its sibling PEEKB/PEEKW/PEEKD cases. Fixed by restoring the obviously-correct sibling-matching value.
- **A real missing/never-migrated file**: `src/runtime/browser/runtime_browser_hook.fbs` didn't exist at all. Per [[feedback-no-placeholders-ever]], did NOT leave it as an empty stub — wrote a real, designed implementation: `UXBRuntimeBrowserDispatch` honestly reports that BROWSER/WASM_BRIDGE/HOST runtime services (Canvas/Audio/Fetch/HostCall) have no native/AST-interpreter implementation and require `--target js`/`--target wasm`, matching this exact family's existing "BROWSER_ONLY" classification in `runtime_service_matrix.fbs`.
- **A real missing function parameter**: `UXBWasmEmitFunction` didn't take a `module As MIRModule` parameter it needed to pass through to `UXBWasmEmitOneInstruction` — added it and updated its one call site.
- **A wrong struct field name**: `inst->resultName` should have been `inst->result` (the only field that actually exists on `MIRIRInstruction`).
- **Missing function arguments**: two `MIRRegisterArrayGlobal module, varName2` calls (REDIM, one pre-existing, one in this session's own new multi-dim code, copied from the pre-existing pattern) were missing the function's 3rd required parameter — fixed by passing `""` (the function's own designed default-to-"ARRAY" case).
- **Unescaped embedded quotes in generated JavaScript**: `src/codegen/js/runtime/js_runtime_embedded_generated.fbs` builds a large JS runtime as one big FreeBASIC string; several lines forgot that an embedded `"` inside an already-double-quoted FB string literal must be doubled (`""`) to escape it, breaking the FB string literal itself mid-line. Fixed ~9 occurrences by doubling the quotes, matching the correct pattern already used elsewhere in the same file.
- **A duplicate `Dim`**: `entryIndex` declared twice in one function in `js_emitter.fbs` (no logic difference, just redundant).
- **A real regression, found only via empirical re-testing after the clean build**: once `UXBFindArrayMemoryInfo`/array-SIZEOF support was added (this codebase's own PATCH4-era work), `SIZEOF(PlainTypeName)` for a bare identifier (e.g. a STRUCT/UNION/TYPE name written without array syntax) started failing outright with "SIZEOF identifier is not a declared array" — the array-lookup path had no fallback to the pre-existing type-name path. This existed in **two independent implementations** (the semantic-pass validator in `layout_path_and_intrinsic.fbs`, and the AST interpreter's own runtime evaluator in `exec_eval_builtin_categories.fbs`) — both fixed identically: fall through to `TypeLayoutSizeOf`/type-name resolution when the identifier isn't a declared array, instead of erroring immediately. **This directly affected the earlier STRUCT/UNION empirical "victory" claim in [[uxb-fix-plan-decisions-2026-09]] — that test was run against a pre-existing binary that predated this regression; after the clean rebuild, the same test failed until this was fixed, then passed again.** Lesson: a from-scratch build can surface real regressions invisible to whatever binary happens to be sitting in `bin/`; the earlier "audit finding was wrong" conclusion for STRUCT/UNION is still correct (the layout engine itself is sound), but this SIZEOF-on-bare-type-name gap was a genuinely separate, real bug this rebuild uncovered.
