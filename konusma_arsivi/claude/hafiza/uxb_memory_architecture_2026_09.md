**Context**: this decision closes out [[uxb-fix-plan-decisions-2026-09]]'s S-036 (MEMCOPYD silently copying zeros) by settling a much bigger, previously-unresolved architecture question the user had been carrying since the language's early design phase. The user presented (2026-09-13/14) a long, well-researched chronological analysis of how uXBasic's memory model evolved (1 MiB toy virtual RAM → hybrid `<1MiB=virtual/>=1MiB=real` heuristic in the x64 backend → NATIVE/VIRTUAL/EXTERNAL concept discussed 2026-08-09 but never fully implemented → today's S-036 discovery that arrays have NO real backing address at all in most engines). Codex independently converged on the same target design from the same document (posted to `ai_koordinasyon/SORULAR_CEVAPLAR.md`, includes a `MemoryRef` abstraction proposal). This memory is the durable record of the LOCKED design; see the coordination log for the full back-and-forth.

## The locked design

1. **NATIVE is the primary model, not a fallback.** `VARPTR`, pointer arithmetic, `PEEK*`/`POKE*`, `MEMCOPY*`/`MEMFILL*` operate on real, addressable process memory by default. A uXBasic program cannot PEEK/POKE arbitrary OS/physical RAM (Windows user-mode has no such right without drivers) — "real memory" means "this process's own address space."
2. **Arrays (including STRUCT-element arrays) get exactly ONE real backing storage, never a second VM-mirrored copy.** `VARPTR(array)` = the address of that one real buffer (= `VARPTR(array(LBOUND(array)))`). Indexed reads/writes (`a(i)=x`), `PEEK*`/`POKE*` through `VARPTR`, and `MEMCOPY*`/`MEMFILL*` through that same address must all observe each other's effects immediately — no "copy into VM, forget to sync back" failure mode (that IS S-036's root cause, confirmed independently by both Claude 1's AST-interpreter trace and Codex's own source reading).
3. **VIRTUAL is an explicit, opt-in, separate address space** — not triggered by address magnitude (the current x64 `<1MiB` heuristic in `__uxb_mem_resolve` is explicitly rejected as bad design). Selected via the `NATIVE`/`VIRTUAL` mode keyword that already exists in the parser/AST for `PEEK*`/`POKE*`/`MEMCOPY*`/`MEMFILL*` (`ExecMemoryModeOffset` in `exec_stmt_memory_core.fbs`) — today the AST interpreter's `NATIVE` mode is deliberately rejected ("NATIVE memory is unavailable in interpreter"); that rejection must be lifted since NATIVE is now the default/primary path.
4. **EXTERNAL is not a separate technical region** — a DLL/API-returned buffer address is just an ordinary real address inside NATIVE's address space; no separate code path needed beyond "don't refuse it."
5. **New user-requested feature, layered on top of #3**: VIRTUAL's size is configurable, and can optionally extend onto disk. Locked syntax: `VIRTUAL <ramSize>[, <diskSize>]` as a real BASIC statement (e.g. `VIRTUAL 2M, 16G` = 2 MB RAM-backed + 16 GB disk-backed extension), size suffixes `K`/`M`/`G` are 1024-based. A CLI flag with the identical syntax (`--virtual=2M,16G`) sets the program's default before it starts; the in-program `VIRTUAL` statement can (re)configure it at runtime (re-issuing it discards prior VIRTUAL-space contents, like `REDIM` without `PRESERVE` — no live-resize-preserving-data complexity). Disk-backed portion should use a Windows memory-mapped file (`CreateFileMapping`/`MapViewOfFile`) rather than a hand-rolled swap system — let the OS's own paging handle the RAM/disk tradeoff transparently.
6. **Pointer arithmetic is byte-based always** (`p + 1` = next byte, never "next element of whatever type"). For typed array element addressing: `address = baseAddress + (index - lowerBound) * elementStride`, and `elementStride` must be the type's real `SIZEOF`, never a hardcoded assumption (Codex found at least one place in the x64 static-array backend that hardcodes 8 bytes regardless of element type — must be found and fixed as part of this).
7. **No width loss in the PEEK/POKE/MEMCOPY/MEMFILL family.** Codex found that the x64 MIR runtime-call layer collapses `PEEKB/W/D` → a single 64-bit `MIRX64EmitRuntimePeekI64`/`PokeI64` helper regardless of the requested width — this silently discards width information at exactly the wrong layer and must be fixed so B/W/D widths survive all the way to the actual memory access. A new **Q (64-bit) family** (`PEEKQ`/`POKEQ`/`MEMCOPYQ`/`MEMFILLQ`) should be added alongside B/W/D for completeness, now that uXBasic is a real x64-targeting language.
8. **MEMCOPY's canonical argument order is locked as `dst, src, count`** (matches the docs and the MIR contract). A real, independent, already-found inconsistency: the legacy AST-direct x64 backend's `X64EmitMemCopyStmt` treats its operands as `src, dst, len` — the reverse — and must be corrected to match.
9. **LIST/DICT/SET remain excluded from raw memory access** (no `VARPTR`/`PEEK`/`POKE`/`MEMCOPY` on their internal GLib-backed representation) — this boundary was already correct and stays as-is; only `ARRAY`/`STRUCT`/`STRUCT ARRAY`/scalars/POD-like types get a raw memory view.
10. **`REDIM` may relocate an array's backing storage; a `VARPTR` taken before `REDIM` is not guaranteed valid after it** (documented `realloc`-like semantics, not a bug to "fix" by adding pointer-tracking machinery — deliberately kept simple).
11. **Codex's proposed unifying abstraction**: a shared `MemoryRef` record (`kind`, `owner`, `baseAddress`, `byteOffset`, `byteLength`, `elementStride`, `writable`, `generation`) that every memory-touching op (`VARPTR`/`PEEK*`/`POKE*`/`MEMCOPY*`/`MEMFILL*`) resolves through via one `ResolveMemoryRef()`, instead of each op re-deriving "is this scalar/array/struct" independently. Agreed as the right END STATE, but Claude 1's stated implementation order is: get each engine's OBSERVABLE behavior correct first (single array backing storage, no width loss, correct stride) via more surgical per-engine fixes, THEN fold the logic into the shared abstraction if it doesn't cost another full pass — reversing that order risks a long half-finished refactor that runs nothing correctly in the meantime.

## Implementation order Claude 1 committed to (smallest/independent first)

(a) MEMCOPY canonical parameter order fix + add the Q (64-bit) family.
(b) Fix x64's PEEK/POKE width collapsing to 64-bit at the MIR runtime-call layer.
(c) **The S-036 core**: give the AST interpreter's arrays one real, contiguous backing buffer; make `VARPTR`/`PEEK*`/`POKE*`/`MEMCOPY*` read/write that same buffer instead of a disconnected VM space.
(d) Same for the canonical-MIR interpreter (`MIRValue elements()`-based array storage today; needs the same single-backing-storage treatment).
(e) Native x64: fix the hardcoded-8-byte `elementStride` bug and make `VARPTR` resolve to the array's real address instead of the `<1MiB` magnitude heuristic.
(f) The new `VIRTUAL <ram>[,<disk>]` statement (parser + semantic + all four engines) plus the matching CLI flag and the memory-mapped-file-backed disk extension.

Each step gets verified with a real compile-and-run (not just a read-through) before moving to the next, per this project's standing "verify by actually running it" rule — see [[feedback_no_placeholders_ever]] and [[feedback_verify_before_destructive_action]].

**2026-09-18 design reminder from Mete (supersedes the loose wording above, but with ONE open conflict):** four concepts — `VIRTUAL` (uXBasic-managed safe space, address = offset inside it, RAM- or file/disk-backed via Windows services), `NATIVE` (real process address), `EXTERNAL` (DLL/API/foreign-runtime memory), and `AUTO`, which is NOT a memory region but a *resolver* that picks VIRTUAL/NATIVE/EXTERNAL from the reference's ORIGIN (typed pointers like `VIRTUAL PTR`/`PTR`/`EXTERNAL PTR`), never from the address's numeric size (the old `<1MiB=virtual` rule is explicitly retired). Raw untyped numbers need a separate default policy — still undecided. **Conflict to resolve**: locked item 4 above says EXTERNAL is NOT a separate region (just an ordinary NATIVE address), while the 2026-09-18 description makes it a distinct mode — ask which is final before implementing anything typed. The earlier S-066 fix ("AUTO resolves like VIRTUAL") is only an interim shared policy for raw AUTO numbers across the 3 main engines, NOT the final meaning of AUTO; tracked as S-069 in `ai_koordinasyon/SORUN_TAKIP.md` (`KARAR-BEKLIYOR`). **2026-09-19 DECISION LOCKED by Mete (resolves the EXTERNAL conflict + AUTO):** memory CLASS is only `VIRTUAL` or `NATIVE`; `EXTERNAL` is NOT a class — a DLL/API pointer is a real process address (NATIVE) whose *origin* is EXTERNAL (kept in a future `MemoryRef.origin`). Selection is `AUTO`/`VIRTUAL`/`NATIVE`; an explicit mode always beats AUTO. **AUTO = by the address expression's static TYPE: pointer-typed (`PTR` family — VARPTR, SADD, PTR(), CASTPTR(), PTR var, `p ± n`) → NATIVE; any plain integer, however big → VIRTUAL.** `PTR(1000)` means real address 1000, `POKED 1000,7` means virtual offset 1000, `CASTPTR(n)` is the programmer's "this number is an address" declaration.
